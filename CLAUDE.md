## Project-specific notes

- Target chip: `esp32s3`; keep dependencies, HAL features, and examples compatible with this chip.
- Board: ESP32-S3-DevKitC-1.
- Check the `generator parameters:` comments in `src/bin/main.rs` before changing code that depends on selected generation options.
- This is a `#![no_std]` / `#![no_main]` project. Avoid `std`; use `core` and embedded-friendly crates.
- `alloc` is enabled. The heap is initialized in `src/bin/main.rs` with `esp_alloc::heap_allocator!`; adjust the heap size there if allocations fail.
- `.cargo/config.toml` contains the generated target, runner, build flags, and `[env]` defaults. Espressif crates expose additional configuration through environment variables; use `esp-config` to inspect/set those options. The linked "Additional configuration" sections for the enabled Espressif crates document crate-specific variables; keep project-specific defaults in `[env]` instead of hard-coding them in source.
- Logging uses `defmt`; the default filter is `DEFMT_LOG=info` in `.cargo/config.toml` and can be overridden from the environment.
- `cargo run` uses `probe-rs` as configured in `.cargo/config.toml`. This path is intended for RTT/defmt and debugging and requires a supported debug probe/JTAG connection, not a USB-UART-only serial adapter.
- If flashing or debugging fails, check `probe-rs list`, probe permissions/udev rules, board wiring/JTAG support, and that the `--chip` in `.cargo/config.toml` matches the target.

## Project purpose

This node acts as a Wi-Fi repeater/extender for the user's own home network (not a public-facing
product): it joins the home router as a station (STA) and simultaneously runs its own access point
(AP), forwarding/NATing traffic between the two so AP clients reach the router/internet. This is a
legitimate home-networking use of ESP32 Wi-Fi extender/repeater functionality — not mesh in the
ESP-WIFI-MESH/Zigbee/Thread sense, and not for intercepting or impersonating networks that aren't
the user's own.

- Networking stack: `esp-rtos` + Embassy async executor (`#[esp_rtos::main]`, `embassy-executor`,
  `embassy-time`). Keep the AP/STA bridging logic as async tasks rather than converting to a
  blocking loop or `esp-rtos` threads.
- Wi-Fi mode: `esp-radio`'s `WifiController` with `Config::AccessPointStation` (concurrent AP+STA),
  as already scaffolded in `src/bin/main.rs`. STA side connects to the home router using
  `SSID`/`PASSWORD` env vars; AP side serves clients under `AP_SSID`.
- Traffic forwarding between the STA and AP interfaces (NAT/routing, DHCP for AP clients) should be
  built on `embassy-net` + `smoltcp`, both already in `Cargo.toml` with the relevant features
  (`dhcpv4`, `tcp`, `udp`, `proto-dhcpv4`, `proto-ipv4`, etc.). See `edge-net` (linked in
  `Cargo.toml`) for additional networking protocol support if needed.
- `SSID`, `PASSWORD`, and `AP_SSID` are supplied as build-time env vars (`env!(...)` in
  `src/bin/main.rs`) — set them in `.cargo/config.toml` `[env]` or the shell environment, never
  hard-code real credentials in source or commit them.

## Learning mode

This project doubles as how the user is learning embedded Rust. They already know Rust; `no_std`,
HAL/peripherals, async-on-embedded (esp-rtos/Embassy), and Wi-Fi/networking-on-MCU concepts are new
to them. Teach, don't just deliver.

- **New concepts (e.g. a HAL API, `no_std` constraint, RTOS/async-on-embedded idea):** use a
  Socratic approach first — ask a guiding question or two and let the user attempt an answer before
  explaining. Don't abandon this at the first wrong answer; give another nudge before correcting.
  Keep it collaborative, not interrogation-style.
- **Stuck on a bug or implementation task:** give a hint toward the likely cause (point at the
  relevant code, error, or doc section) and withhold the actual fix. Only give the full fix if the
  user asks directly or stays stuck after another hint.
- **Anchor explanations in a mix of:** (a) this repo's actual code (`src/bin/main.rs`, the
  AP+STA/esp-radio/embassy-net setup) and (b) general real-world embedded/networking scenarios —
  blend both rather than picking only one.
- Don't over-explain things the user already knows from general Rust (ownership, traits, error
  handling basics) — focus teaching effort on what's embedded/HAL/RTOS/Wi-Fi-specific.
